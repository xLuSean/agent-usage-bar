# Claude 的額度資料來源

App 如何取得 Claude 的方案額度：欄位、格式與容錯策略。Codex 那一側見 [CODEX_USAGE.md](CODEX_USAGE.md)；兩者共用的邊界與視覺語言見 [SAFETY.md](SAFETY.md) 與 [UI_SPEC.md](UI_SPEC.md)。

**App 自己不發任何 HTTP 請求。** 數字來自官方 CLI 的一個固定唯讀指令。

舊的「鑰匙圈 ＋ 未文件化 OAuth endpoint」原型已於 0.3.0 完整退場，公開版本沒有該路徑也沒有自動 fallback。當初那條路怎麼做的、踩到什麼、以及什麼情況下值得走回去，記在 [LEGACY_KEYCHAIN_PATH.md](LEGACY_KEYCHAIN_PATH.md)。

## 1. Claude：一個固定的唯讀指令

```bash
claude --safe-mode --no-session-persistence -p "/usage" --output-format json --verbose
```

參數是常數（`ClaudeUsageCommand.arguments`），沒有設定介面餵它，也沒有任何回應能影響它。不經 shell，直接以 `Process.executableURL` 執行驗證過的一般檔案。

`--verbose` 只改變**印出什麼**，不改變**執行什麼**。沒有它，輸出只有最後一則結果訊息；有它，輸出是這次執行每一則訊息組成的一個 JSON 陣列，其中遞送 `/usage` 的那一則附有結構化的用量報告（§3）。2026-10-11 以 Claude Code 2.1.287 實測，加上後仍是 `num_turns=0`、所有 token 計數 0、`total_cost_usd=0`。

## 2. 一份輸出，兩個來源

陣列裡只有兩樣東西進入解碼：

| 位置 | 內容 |
|---|---|
| `type` 為 `result` 的那一則訊息 | 成功訊號 `is_error`、`subtype`，以及給人閱讀的英文文字 `result` |
| `type` 為 `assistant` 的訊息上的 `usage_report` | 同一批額度數字的結構化版本 |

`result` 訊息必須恰好一則；`is_error` 必須是 `false`，**缺這個欄位視同錯誤** —— 沒有成功訊號不等於成功；`subtype` 必須是 `"success"`。`usage_report` 最多一份，多於一份就不知道該信哪一份。

其餘一律不讀、不保存、不顯示，也不會出現在任何錯誤訊息裡：

- 開頭的 `init` 訊息。它列出工作目錄、session，以及這次執行的每個工具與指令。
- `assistant` 訊息裡的 `local_command_source`，以及 `result` 文字後半的本機活動統計 —— 請求數、session 數、用了哪些 skill 與 MCP server 及其占比。那是**使用者的私人工作紀錄**，而且與百分比不同來源（前者由本機 session log 算出，後者來自伺服器的限額資料）。
- 每一則訊息上的一次性 `session_id`。
- `result` 訊息的 `usage` 物件。它描述的是這次 CLI 呼叫本身的 token 數（全部為 0），**不是方案額度**，不可誤用。

不帶 `--verbose` 時的輸出是單一 JSON 物件，也就是那一則 `result` 訊息本身。解碼器仍接受這個形狀，視同「沒有附報告」。

### 2.1 該讀哪一個

| 輸出裡有 | App 的做法 |
|---|---|
| 沒有 `usage_report` | 讀文字（§4） |
| 有報告，但 `rate_limits` 或 `limits` 是 `null` | 回報 `claudeUsageUnavailable`。**不讀文字** |
| 有報告，`limits` 是空陣列 | `schemaChanged` |
| 有報告，列裡同時有 session 與 weekly | 讀列（§3） |
| 有報告、有列，但缺 session 或 weekly 其中之一 | 讀文字（§4） |

第二列是整個設計的重點。Claude Code 連不上用量服務時，文字照樣印出它最後知道的數字，而且沒有任何標記說那是舊的；報告則直接說「沒有」。這時若退回去讀文字，就是把「這次沒查到」重新變成一個有自信的數字 —— 而報告存在的意義正是擋掉這件事。App 改走失敗路徑：保留自己上一筆成功的讀數並標示為過期。

最後一列是還沒觀察到的形狀。兩段 session 之間沒有進行中的時間窗（§4.1），文字印 `0%` 且沒有 reset；報告可能用一列 `percent: 0`、`resets_at: null` 表示，也可能乾脆不列。若是後者，伺服器確實回答了，文字與列一樣新，所以讀文字，而不是讓 App 在每一段閒置空檔都停在錯誤上。

沒有附報告有兩種正常原因：Claude Code 版本較舊（官方文件記載 Agent SDK 0.3.273 起才有這個欄位）；或登入不符合附報告的條件 —— 官方列的條件是以 claude.ai 憑證登入、憑證帶有已知方案或讀取方案資料的權限、且帳號不是按用量計費。兩種情況都不是錯誤。

官方把 `usage_report` 標為實驗性，形狀可能改變。所以它不存在永遠不算錯，而 App 依賴的那兩列讀得很嚴。

## 3. 結構化報告的列

`usage_report.rate_limits.limits` 是一個陣列，每一列是一個額度：

| 欄位 | App 怎麼用 |
|---|---|
| `kind` | `session`、`weekly_all`、`weekly_scoped`，或這個版本沒見過的值。分類只看它，不看標籤 |
| `group` | `session`、`weekly` 等 |
| `percent` | 已用百分比，0–100 的數字，可以有小數 |
| `resets_at` | ISO 8601 時間字串，或 `null`。實測同一份輸出裡同時出現帶六位小數秒與不帶小數秒兩種寫法 |
| `scope.model.display_name`、`scope.surface.display_name` | 這一列適用的模型或介面，當作標籤。先取模型，沒有才取介面 |
| `is_active` | 伺服器選來代表帳號目前狀態的那一列，顯示為「目前綁定」 |

**刻意不讀的兩樣：** 每一列的 `severity`，以及 `rate_limits.extra_usage`。前者是伺服器對顏色的建議，而量表顏色只由百分比決定、與 Codex 共用同一套刻度（[UI_SPEC.md](UI_SPEC.md) §3.1）。後者是用量點數的花費，App 顯示的是額度時間窗，不是帳務。`verify.sh` 有護欄防止這兩個 surface 被加回來。

### 3.1 兩種列，兩種嚴格度

量表與保存的讀數都建立在兩個額度上：session 與 all-models weekly。這兩列 fail closed，任何一項對不上就整份失敗：

| 情況 | 結果 |
|---|---|
| 同一種必要額度出現兩列 | `schemaChanged` —— 選哪個都是在賭使用者看到的數字 |
| `percent` 不是 0–100 的數字 | `schemaChanged` —— 不 clamp，clamp 會把誤讀變成一個有自信的 100% |
| `percent` 是布林值 | `schemaChanged` —— JSON 的 `true` 在解析後讀起來是 `1` |
| `resets_at` 不是可解析的時間字串 | `schemaChanged` |
| weekly 的 `resets_at` 是 `null` | `schemaChanged` —— 週窗永遠在跑 |
| session 的 `resets_at` 是 `null` 而百分比不是 0 | `schemaChanged` —— 非零用量卻沒有 reset 是不完整的資料 |
| 任一列的 reset 加 60 秒寬限已經過去 | `claudeUsageOutdated`（§7） |

這幾條與文字路徑（§5）及保存層 `UsageSnapshotStore` 的規則相同。保存層若比解碼器嚴，讀數會被靜靜丟掉、每次啟動都重查；有一項測試專門確認「解得出來的都存得進去」。

其他每一列 —— 現在是各模型的週上限，以後可能是別的 —— 盡力而為：讀得懂就顯示，讀不懂就略過。

| 情況 | 結果 |
|---|---|
| `kind` 或 `group` 不是安全的識別字、`percent` 無效、`resets_at` 無法解析 | 略過這一列 |
| reset 加 60 秒寬限已經過去 | 略過這一列 —— 它描述的窗已經結束 |
| 兩列有相同身分（`kind` 加標籤） | 兩列都略過 |
| 標籤含控制字元、方向控制字元或超過長度上限 | 保留這一列，但不採用標籤，改用通用名稱 |
| 超過 16 列 | 只取前 16 列 |
| 沒見過的 `kind` | 保留，以它自己的名字顯示 |

理由：一個這個版本讀不懂的新額度，不該把那兩個必要數字一起拖垮；而略過一列永遠不會讓錯的數字出現在畫面上。代價是使用者不會知道有一列被略過。

## 4. 文字備援

沒有報告可讀時（§2.1），數字來自 `result` 這段為人閱讀的英文散文，**沒有欄位 schema**。下列數字與時間只示範格式，不是任何真實帳號的讀數：

```text
Current session: 40% used · resets Jan 15 at 1am (Etc/UTC)
Current week (all models): 10% used · resets Jan 19 at 12pm (Etc/UTC)
```

兩行都必須出現且各只能出現一次。分隔符號是 `·`（U+00B7）。文字裡各模型的週上限那幾行不解析 —— 那是結構化報告才提供的東西。

### 4.1 `Current session` 的 reset 子句是選用的

沒有進行中的時間窗時，它只印百分比：

```text
Current session: 0% used
```

原因是**五小時窗從「上一段結束後第一次使用」起算，不是照時鐘對齊**。實機曾觀察到相鄰重置略超過五小時；中間那段沒有窗，也就沒有 reset 可報。

`Current week (all models)` 的 reset **仍為必要** —— 週窗永遠在跑，它少了 reset 才是真的格式漂移。這個不對稱是刻意的。

### 4.2 重置時間的格式

實測至少兩種形式，解析器必須都接受：

| 形式 | 例子 |
|---|---|
| 含分鐘 | `Jan 15 at 12:59am (Etc/UTC)`（合成示例） |
| 整點省略分鐘 | `Jan 15 at 1am (Etc/UTC)`、`Jan 19 at 12pm (Etc/UTC)`（合成示例） |

三個容易寫錯的地方：

- **12 小時制的 12。** `12am` 是午夜（0 時），`12pm` 是中午（12 時）。天真的「pm 就 +12」兩個都會錯。
- **沒有年份。** 年份由「離現在最近」推出來，否則 12/31 的重置在 1/1 讀到會跳回十一個月前。
- **時區是文字裡指定的**，不是本機時區。用本機時區解讀會讓機器與帳號時區不一致的人每個重置時間都偏掉。未知 IANA timezone 會直接 fail closed，不會退回呼叫端或本機時區猜測。

這三個陷阱都只屬於文字路徑。結構化報告的 `resets_at` 自帶年份與時區偏移。

## 5. 文字路徑的容錯：fail closed

與舊路徑相反。舊的 JSON 端點對壞掉的陣列元素逐一跳過，因為欄位多、缺一個不影響其他。這裡只有兩行，**任何一行對不上就整份失敗**：

| 情況 | 結果 |
|---|---|
| 缺任一行 | `schemaChanged` |
| 同一個窗出現兩行 | `schemaChanged` —— 選哪個都是在賭使用者看到的數字 |
| 百分比 > 100 | `schemaChanged` —— 不 clamp |
| 重置時間無法解析 | `schemaChanged` |
| 非 JSON、`is_error`、非 success subtype、空 `result` | 對應的錯誤 |

**不猜、不補 0%、不沿用舊值。** 顯示「未知」的代價是使用者多看一眼；顯示錯的數字的代價是他照著那個數字做的決定。

## 6. 和 Claude Code 自己的畫面對不上時，多半是那邊比較舊

一次同機、近同時觀察中，本 App 與直接執行 `/usage` 的數字彼此接近；Claude Code 狀態面板的 session 與同一週窗內的 weekly 數字都明顯較舊。這裡只保留相對結論，不公開真實帳號的百分比與取得時間。

**Claude Code 內部不同介面的 usage 資料不是同步的。** 狀態面板會停在某個時間點的快照，`/usage` 則是每次執行時重新取得。本 App 用的是後者。

所以兩邊數字不同時，先看週用量哪一個比較大 —— 大的那個比較新。

## 7. 新鮮度

### 7.1 有報告時：伺服器沒回答就是沒有列

2026-10-11 以 Claude Code 2.1.287 觀察，測試方式是封鎖對外連線後執行同一條指令：

| 距離上一次成功取得 | 報告的列 | 文字 |
|---|---|---|
| 連線正常 | 有 | 有 |
| 約 3 秒，連線已封鎖 | 有，與前一次完全相同 | 有 |
| 約 40 秒，連線已封鎖 | `null` | 有，印的仍是先前的數字 |

兩個結論：

- **列不等於「這一次執行查到的」。** Claude Code 會短暫沿用剛取得的答案，長度沒有文件記載，觀察到的範圍在 3 到 40 秒之間。所以「有列」的意思是「大約一分鐘內來自伺服器」，是一個比文字緊得多的上限，不是時間戳。
- **過了那一小段，查不到就是 `null`，而文字仍然印舊數字。** 這是 App 改讀報告的主要理由（§2.1）。

報告和文字一樣沒有「這筆數字是幾點拿到的」。

### 7.2 沒有報告時：用重置時間當守門

文字連不上伺服器時會安靜地退回 Claude Code 的本機快取。2026-08-28 的一次離線跨窗觀察直接看到上一個窗的百分比與 reset 原封不動回傳；恢復 Wi-Fi 後才取得新窗資料。指令耗時不能用來判斷是否連網，因為離線與連網樣本的時間互相重疊。

守門使用每個必要時間窗的重置時間推出上限：

- 重置時間 + 60 秒寬限 **還沒到** ⇒ 快取寫在當前窗內 ⇒ 最舊不超過一個窗。
- 重置時間**已經過了** ⇒ 這筆讀數描述一個結束了的窗 ⇒ `claudeUsageOutdated`，顯示不可用。

寬限吸收時鐘誤差，以及「真實邊界 00:59:59 vs 文字寫 1am」這一秒。

session 與 weekly 兩個必要時間窗都逐一檢查；任何一個 reset 已跨界，整份讀數都不可用。守門擋不到窗內的落後，因此在文字路徑上 session 最壞可接近 5 小時舊。

### 7.3 守門對報告的列也照樣執行

「有列就夠新」是對單一 CLI 版本的觀察，不是契約。檢查通過時沒有成本，所以兩個必要額度不論來自哪一個來源都過同一道守門。

## 8. 文字路徑守門的關鍵假設：一次離線跨窗觀察

守門要成立，得排除兩種機制完全不同的失效方式：

- **(A) 重置時間自己往前跑** —— 值若是相對的、每次重算，舊快取也會長出新的重置時間。
- **(B) 窗滾動時被改寫** —— 寫入新的重置時間，卻沿用舊的百分比。

**(A) 已排除。** 一次性檢視 Claude Code 記錄的 rate-limit 資料：

```text
rateLimitType: 'five_hour'
resetsAt:      <absolute Unix timestamp>
```

是絕對 Unix 時間戳，不是可重算的相對值。寫死的整數不會自己前進，所以放著不動的舊快取必然帶著舊的重置時間。該整數也與同期 `/usage` 文字顯示的重置時刻吻合。

**(B) 在一次離線跨窗觀察中沒有發生。** 測試機只有 Wi-Fi；關閉 Wi-Fi、跨過 reset 並等過 60 秒寬限後，仍收到上一個窗的非零百分比與舊 reset。兩個舊欄位一起保留，App 會正確判定過期。恢復 Wi-Fi 後再次查詢，才改為 `Current session: 0% used`，且沒有 reset 子句。

腳本把仍留在路由表裡的預設路線誤判成 `net=online`；那不是實際連線證據。測試機沒有其他網路介面，Wi-Fi 當時確實關閉。日後不得用路由項目或 `duration_ms` 代替真正的連線狀態。

**守門本身不會被繞過，這一條由 source 保證。** weekly 的重置時間在兩條路徑上都是必要的，session 的才是選用，所以每份被接受的讀數至少帶一個 `resetsAt` 進入檢查。但 weekly 的重置一週才動一次 —— 一份「新 session 重置 + 舊百分比」的讀數，仍可能從還有好幾天才到期的 weekly 重置底下通過。

這次結果支持現行守門，但證據範圍只有**單一樣本、單一 CLI 版本**。正確說法是「這次沒有發生 (B)」，不是「Claude Code 永遠不會發生 (B)」。Claude Code 2.1.243 的更新紀錄提到修正過「時間窗重設後、session 閒置期間仍顯示重設前的百分比」，那正是 (B) 這一類行為；這個觀察早於該版本，尚未在新版重做。

> 這次檢視是一次性診斷。App **不讀** Claude Code 的內部檔案，也不以它為備援。

## 9. 失敗分類

非零 exit 時讀 stderr 與 stdout **只為了分類**，內容不進 UI、不進 log、不進錯誤訊息。

stdout 是 `--verbose` 的陣列時，只取 `result` 訊息自己的文字來分類。陣列的第一則訊息列出這次執行的工具與指令名稱；直接取輸出開頭的一段，會讀不到排在最後的結果，還可能拿某個工具的名字去比對關鍵字。stdout 不是陣列時（例如舊版直接拒絕參數），照舊取開頭的一段。

| 訊號 | 錯誤 | 提供的指令 |
|---|---|---|
| `unknown option`、`unrecognized option` 等 | `claudeVersionUnsupported` | 無（要更新，形式依安裝方式而異） |
| `not logged in`、`please sign in` 等 | `claudeNotSignedIn` | `claude` |
| 其他 | `claudeCommandFailed`（只帶 exit code） | 無 |
| 逾時 30 秒 | `claudeCommandTimedOut` | 無 |
| 找不到／不可執行 | `claudeExecutableNotFound`／`Invalid` | 無（要安裝或指定路徑） |

版本訊號優先於登入訊號：舊版拒絕 `--safe-mode` 時常會連帶印出提到登入的說明文字，而「更新 Claude Code」才是真正有用的那一步。

指令本身成功（exit 0、`is_error=false`）但報告沒有列，是另一種失敗：`claudeUsageUnavailable`。它不提供登入指令 —— 一次沒查到不是登入能修好的。若先前有成功的讀數，畫面保留它並標示為過期。

## 10. 已驗證 vs 未驗證

**已驗證（2026-08-24，Claude Code 2.1.231）**

- 不帶 `--verbose` 的指令成功回傳，`is_error=false`、`num_turns=0`、所有 token 計數 0、`total_cost_usd=0`。
- 文字的兩種重置時間格式都實際出現過。
- 斷網時文字仍回傳數字；指令耗時不能區分離線與連網。
- 2026-08-28 離線跨窗時，文字的舊百分比與舊 reset 一起保留，守門正確拒絕；恢復 Wi-Fi 後取得 `0%`、無 reset 的新窗輸出。
- CLI 與退役端點在近時間讀取時落在合理變化範圍內，重置時間一致。
- Claude Code 的狀態面板與 `/usage` 可能給出不同數字；本 App 用的 `/usage` 是較新的那一個（§6）。

**已驗證（2026-10-11，Claude Code 2.1.287）**

- 帶 `--verbose` 的指令輸出一個含三則訊息的陣列，`assistant` 那一則附有 `usage_report`；仍然不跑模型、不耗額度。只帶 `--output-format json` 的輸出沒有這個欄位。
- 在模擬 App 的乾淨環境（只保留必要環境變數，由 Claude Code 自己的登入取得資料）下同樣拿得到報告的列。
- 報告的列包含 session、all-models weekly 與一個模型專屬的週上限；`is_active` 會隨帳號狀態落在不同列上。
- `resets_at` 在同一份輸出裡同時出現帶六位小數秒與不帶小數秒兩種寫法，解析器兩種都接受。
- 封鎖連線後的行為如 §7.1 的表格。
- 以實際輸出跑過現行解碼器：連線時解出三個時間窗，封鎖連線後得到 `claudeUsageUnavailable`；實際輸出的開頭訊息不會被誤判成未登入。實際輸出沒有保存。
- Claude Code 每次執行都會在自己的暫存根目錄留下一個以工作目錄命名的資料夾。在連得到伺服器的乾淨環境、路徑長度不短於實際查詢目錄的位置執行：不帶 `CLAUDE_CODE_TMPDIR` 時每次多一個；帶上並指向查詢目錄後不再新增，而且拿到的仍是報告的列，不是離線時的 `null`。App 現在固定帶這個變數，理由見 [ARCHITECTURE.md](ARCHITECTURE.md) §12。

**未驗證**

- 用量服務**對這個帳號限流**時，報告是 `null` 還是帶著上次已知的列。官方更新紀錄提到互動畫面在這種情況會顯示「上次已知」的長條。若是後者，App 會把它當成一般讀數顯示，只剩重置時間守門；沒有在真實帳號上觸發限流來測。
- 封鎖連線的觀察是用封鎖對外連線的方式做的，不是實際關閉網路介面；也只有單一版本、少數樣本。
- 兩段 session 之間的空檔，報告用什麼形狀表示（§2.1 最後一列）。
- `usage_report` 的長期穩定性。官方標為實驗性。
- 文字格式的長期穩定性。沒有公開 schema，隨時可能改。
- 文字是否會依系統語言在地化。子程序的 `LANG`／`LC_ALL` 已固定為英文，但解析器不依賴它。
- 其他 Claude Code 版本或其他時間窗的跨窗行為；目前只有一次直接觀察，而且早於 2.1.243 的相關修正（§8）。
- `/usage` 是否反映不經過 Claude Code 的用量，例如 Claude Desktop 或 claude.ai。
- 支援 `/usage` 的最低 Claude Code 版本。不硬編，以執行結果判定。
- 其他 Claude Code 版本在暫存根目錄指向深層路徑時的行為。官方更新紀錄提過深層路徑曾造成問題並已修正；這裡只實測過上述單一版本。

## 11. 視窗身分的映射

`/usage` 的文字稱短期限制為 `Current session`，報告稱它 `session`，兩者都沒有「5 hours」。App 沿用既有的 5 小時標籤（`UsageWindow.Kind.session`）以維持 UI 一致，但那是一個**映射，不是它自己說的**。`Current week (all models)`／`weekly_all` 對到 `weeklyAll`，`weekly_scoped` 對到 `weeklyScoped` 並以「7 天 · 標籤」顯示。

「目前綁定」只來自報告的 `is_active`。文字沒有說哪一個限制正在綁定，所以走文字路徑時 `isActive` 一律為 `false` —— 從百分比高低猜會把「目前綁定」的標記貼在一個推論上。

選單列量表不受 `is_active` 影響，仍然顯示最短的那個時間窗（[UI_SPEC.md](UI_SPEC.md) §1）。
