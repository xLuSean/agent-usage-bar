# 已退場的路徑 —— 鑰匙圈 + `/api/oauth/usage`

記錄日期：2026-08-24
狀態：**已從產品移除**，改用 `claude -p "/usage"`（見 [CLAUDE_USAGE.md](CLAUDE_USAGE.md)）

這份文件的存在理由很單純：程式碼 git 撈得回來，**判斷撈不回來**。下面記的是當初為什麼那樣寫、哪些細節是踩出來的、以及什麼情況下值得走回頭路。

## 1. 為什麼只保留判斷，不保留還原指南

舊實作刻意不會帶進公開版的 Git 歷史；這份文件只保留當時驗證出的行為、風險與決策理由，不提供可直接還原 credential locator、request fingerprint 或 refresh 流程的指南。若未來真的要重啟這條路，必須把它當成新的安全設計重新驗證，不能照抄歷史觀察。

## 2. 這條路實際上做什麼

宿主 App 直接從 macOS credential storage 取出 Claude Code 的 OAuth 登入資料，再呼叫一個未公開保證的帳號用量端點。請求必須模擬官方 CLI 的客戶端識別；回應再被轉成時間窗、百分比與重置時間。

這裡刻意不列 credential item 名稱、內部 JSON 欄位、完整 URL 或 headers。那些細節不是公開 API 契約，公開它們只會讓退役路徑更容易被不加思考地重建。

**這是即時查詢，帳號層級，跨裝置正確。** 這是它相對新路徑唯一的、但也是實質的優勢。

## 3. 不在程式碼裡的知識

### 3.1 客戶端指紋不是穩定契約

端點會依客戶端識別套用不同限制；舊實作因此不得不模擬官方 CLI。代價是**這個 App 在連線上無法與官方 CLI 區分**，且上游只要改變未公開規則，所有安裝就可能同時失效。這也是不能把當時觀察當成永久規格的原因。

### 3.2 鑰匙圈授權對話框是結構性的，不是 bug

實測顯示，建立 credential 的通用系統工具可靜默讀取；宿主 App 則會觸發授權對話框。Claude Code 續期時還可能重建整筆項目，使使用者先前給宿主 App 的授權失效。換句話說，反覆提示是這個 ownership 與 ACL 模型的結果，不是單純 UI bug。

更重要的是：依賴通用系統工具繞過提示並不會形成可靠的 App 身分邊界，反而會擴大同一使用者下可讀取秘密的程式範圍。因此公開版完全移除這個選項。

### 3.3 憑證有兩個到期時間

登入資料包含短效存取票與較長效的續期票。這解釋了全部現象：

| access token | refresh token | 執行 `claude` 的結果 |
|---|---|---|
| 過期 | 仍有效 | 靜默續期，不需要登入 |
| 過期 | 也過期／已撤銷 | 要求登入 |

**只有 Claude Code 會續期這組登入。** Claude Desktop 使用另一套登入狀態，不會替 CLI 的 credential 續期。所以主要使用 Desktop 的人，舊資料來源會週期性失效。

App 自己不換票：憑證裡雖然有 refresh token，但用掉它通常會讓舊的作廢，而 App 對鑰匙圈是唯讀的，換了票寫不回去反而會弄壞 Claude Code 的登入。

### 3.4 退避上限必須大於懲罰窗

舊端點的限流以**帳號**計算，且在懲罰期內重試可能重新計時。因此退避上限必須大於觀察到的懲罰窗；否則每次重試都可能重啟懲罰，形成無法恢復的循環。這是退役設計的歷史教訓，不是現行 CLI 路徑的設定值。

### 3.5 百分比的尺度陷阱

`limits[].percent` 是 0–100，但另一個舊回應欄位的 `utilization` 是 0–1，兩者名字很像。以合成數字為例，混用會把 25% 變成 0.25%。`UsedPercent` 把尺度帶在型別上就是為了擋這件事，所以整條管線只有 `usedPercent` 一個四捨五入點。

**這個型別在新路徑仍然需要**，沒有跟著刪。

### 3.6 `limits[]` 以外的欄位全部是噪音

回應還帶 `five_hour` / `seven_day` 相容物件，以及一批內部代號欄位（`amber_ladder`、`cinder_cove`、`iguana_necktie`、`nimbus_quill`、`omelette_promotional`、`tangelo`、`seven_day_cowork` 等）。那些是未發布功能的佔位符，名字會變也會消失。

相容物件的 `utilization` 也不能拿來算數 —— 它跟 0–1 的舊欄位同名，但這裡的尺度從來沒確認過，而**從數值大小反推尺度**正是前述合成例子要說明的錯誤。

### 3.7 為什麼用 `JSONSerialization` 不用 `Codable`

每個欄位都必須是 optional，而且某個陣列元素型別變了不能連累其他元素。這條路上的資料來自一個未文件化、可能無預警改變的端點，逐元素跳過比整包失敗合理。

## 4. 為什麼離開

不是因為它不能用 —— 它能用，而且拿得到即時、跨裝置正確的數字。離開是因為**它要求 App 接觸 OAuth 憑證**，而憑證一經手，下面全部變成我們的問題：鑰匙圈 ACL、授權對話框、格式驗證、scope、8 小時到期、401、403、429、User-Agent 冒充、未文件化端點隨時可能改變。

這個專案到目前為止絕大部分的複雜度、風險與踩過的坑都集中在這一塊。換成 `claude -p "/usage"` 之後，這一整類問題一次消失。

## 5. 新路徑的已知弱點 —— 什麼情況下值得走回來

新路徑不是純粹的升級，是取捨。

### 5.1 它連網時會更新，離線時退回快取

早期曾以斷網與連網的單次耗時差距推測網路往返。後續觀察否定了這個判斷方式：同一批樣本中，離線與連網耗時互相重疊，`duration_ms` 不能證明資料來源。

目前較直接的證據來自內容：只有 Wi-Fi 的測試機關閉 Wi-Fi、跨過已知 reset 後，`/usage` 仍回傳上一個窗的完整舊資料；恢復 Wi-Fi 後再次查詢才取得新窗資料。因此現行版本的離線路徑會退回快取，但這仍不是 Claude Code 的公開契約。

【仍待驗證】`/usage` 是否反映不經過 Claude Code 的使用量，例如 Claude Desktop 或 claude.ai；需要從那些介面消耗額度後再查一次。

### 5.2 因此仍然存在的弱點

- **離線時數字會靜默偏舊。** 輸出裡沒有「這筆數字是幾點拿到的」，App 無法直接得知它多舊。目前用 reset 時間推出上限：reset 還沒到 ⇒ 快取寫在當前窗內 ⇒ 最舊不超過一個窗（session 是 5 小時）；reset 已過 ⇒ 判定不可用。
- **伺服器查詢失敗時的行為未知。** 連著網但 API 出錯時，它可能同樣靜默退回快取，形態與離線相同。
- **它會發認證請求。** 也就是 App 排程的每一次呼叫，都可能讓 Claude Code 順手續期憑證 —— 誠實的說法是「App 不再**讀**憑證，但它執行的指令可能會**寫**憑證」。

**下列任一條成立時，走回這條路是合理的：**

1. 實測發現 `/usage` 其實只讀快取、不會即時更新，而使用者主要透過 Claude Desktop 或 claude.ai 消耗額度，數字長期落後到沒有參考價值。
2. 實測發現 Claude Code 會在窗滾動時**本機更新 reset 時間但不更新百分比** —— 那樣 §5.2 的守門會失效，而且是靜默失效。（2026-08-28 的單一離線跨窗樣本沒有發生，日後版本仍可能改變；見 [SAFETY.md](SAFETY.md) §3.2。）
3. `/usage` 的文字格式改變且無法可靠剖析，而端點仍然穩定。
4. 需要在**離線或 CLI 故障時**仍拿得到數字。

**回來之前要重新確認的事：** 端點是否還在、回應結構是否還一樣、客戶端識別規則是否還成立、限流懲罰窗多長。這四件全部是未文件化的觀察，放了幾個月之後不能假設仍然為真。

## 6. 對照：兩條路的差異

| | 鑰匙圈 + 端點（舊） | `claude -p "/usage"`（新） |
|---|---|---|
| 資料新鮮度 | 即時 | 連網即時，離線退回快取 |
| 需要接觸憑證 | 是，App 自己讀 | 否，但指令可能寫憑證 |
| 鑰匙圈對話框 | 會，且反覆出現 | 無 |
| 8 小時到期問題 | 有，App 要自己處理 | 無，由 Claude Code 自己處理 |
| 限流風險 | 有，帳號層級，且曾觀察到短期懲罰窗 | 由 CLI 自己承擔 |
| 身分 | 冒充官方 CLI | 就是官方 CLI |
| 介面穩定性 | 未文件化端點 | 文件化指令，但百分比包在人類文字裡 |
| 失敗形態 | 看不到資料 | 離線時可能顯示偏舊的數字 |
